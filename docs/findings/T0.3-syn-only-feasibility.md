# T0.3 — SYN-only feasibility (findings)

**Task:** [T0.3 in implementation-doc.md](../implementation-doc.md#t03--syn-only-feasibility-check)
**Date:** 2026-05-27
**Status:** Static-analysis prediction. **Not empirically verified.**

## Summary

Reading paqet's flag-cycling code top-to-bottom, **a SYN-only profile is plausible
on the send path but has several latent issues that will bite in Phase 1 if not
addressed.** We could not empirically confirm the prediction because the
sudo-gated integration test cannot run on this developer box (no cached sudo,
non-interactive CLI harness; see T0.2 Appendix C for the same constraint). The
test `Test_Smoke_SynOnly` is therefore written, compiling, and skipping cleanly
without root; a future runner with privileges (or Linux CI per T4.5) will tip
this from prediction into measurement. The concrete code-level concerns
catalogued below — most notably loopback link-layer framing already flagged in
T0.2 Appendix C, the unusably-small SYN sequence-number space, and the
kernel-RST window when the firewall rules are not applied — are exactly the
items Phase 1 should fix as it rewrites the I/O path into the new `Transport`
interface.

## How to read this document

This is a **diagnostic** brief, not a fix. Each "Suspected obstacle" entry
points at the file and line that owns the concern and assigns it to the

## Static analysis

### How flags are parsed

`local_flag` / `remote_flag` come in as YAML string lists (e.g. `["S"]`,
`["PA"]`). `internal/conf/tcp.go:strTCPF` walks each character of every entry
and sets the matching field on a `conf.TCPF` struct (one struct per list
entry). The `S` character sets `TCPF.SYN=true` and nothing else. The result of
validation is two parallel slices `TCP.LF` and `TCP.RF` of `[]conf.TCPF`.

There is no validation that a flag profile is *useful* (e.g. that at least one
of SYN/PSH/ACK is set, or that the combination wouldn't immediately be
rejected by every real OS stack). `local_flag: ["S"]` is therefore accepted.

### How the iterator cycles

`internal/pkg/iterator/iterator.go` defines a generic round-robin iterator with
an atomic counter. `SendHandle.tcpF` wraps two of these: one for the default
(server's own `LF`) and a per-client map of overrides established by the
`PTCPF` control message. Each outgoing packet calls `Next()` to pick which
`TCPF` to stamp into the TCP header.

When the profile is `["S"]` the iterator returns the same single-element
`TCPF{SYN: true}` on every call. No flag cycling actually happens; it
degenerates to a constant. **This is fine in principle but is a useful mental
note: a SYN-only deployment makes the iterator pure overhead. The Phase 1
Transport refactor can simplify this.**

### What the SYN branch of `buildTCPHeader` does differently

`internal/socket/send_handle.go:126-167`. When `f.SYN` is true:

- Options are: MSS=1460, SACK-permitted, Timestamps (with TSval = a
  monotonic-ish counter, TSecr = 0), one NOP, WindowScale=8. A normal
  client-initiated SYN. Reasonable.
- `tcp.Seq = 1 + (counter & 0x7)` — **only 8 distinct sequence numbers**,
  rotating with the global counter. Two consecutive SYNs to the same 4-tuple
  will trivially collide on `(srcIP, srcPort, dstIP, dstPort, seq)`, which any
  receiver tracking SYN-flood mitigation (or the loopback IP layer doing
  duplicate-detection during normal kernel processing) may treat as a
  retransmit and silently drop. This is the **single biggest behavioural risk
  for SYN-only mode**: the data plane will appear to work for a handful of
  segments then start losing KCP segments to dedup with no diagnostic surface.
- `tcp.Ack = 0` when `f.ACK == false`. For `["S"]` (SYN only) this is fine.

In the non-SYN branch (`f.SYN == false`), Seq is `time + (counter << 7)` —
~much~ larger entropy, ~no duplicates within a tunnel session.

### What the receive path filters

`internal/socket/recv_handle.go`:

- BPF filter is `tcp and dst port <N>` — **no flag predicate.** SYN packets
  inbound to the tunnel port pass the filter. Good.
- The parser does `gopacket.NewPacket(data, layers.LayerTypeEthernet, ...)`,
  unconditionally treating link layer as Ethernet. Already flagged in T0.2
  Appendix C as a macOS `lo0` blocker (DLT_NULL has no Ethernet header). The
  SYN-only profile inherits this problem unchanged — it is a framing issue,
  not a flag issue.
- `appLayer.Payload()` is the bytes after the TCP header. `gopacket` exposes
  any post-header bytes as the TCP application layer regardless of the SYN
  flag's value (it parses by length, not by flag semantics). So a synthetic
  SYN-with-payload *is* parseable. Good.
- However, the recv path drops any packet without an `ApplicationLayer`
  (`recv_handle.go:71-73`). A SYN packet that happens to carry zero payload —
  e.g. a KCP keepalive that yields an empty segment — would be silently
  dropped. Worth keeping in mind during T1.3's recv refactor.

### KCP-over-SYN-only sequencing assumptions

`internal/tnet/kcp/dial.go` and `listen.go` pass `*socket.PacketConn`
straight into the kcp-go library. KCP treats the wrapped `net.PacketConn` as
unordered datagrams (it provides its own reliable, ordered overlay), so the
TCP flags ctun stamps onto the carrier frames are irrelevant to KCP — every
KCP segment becomes a fresh outgoing `WriteTo` and therefore a fresh ctun
packet. **There is no KCP-side dependency on TCP semantics; SYN-only is a
no-op from KCP's perspective.** The one caveat is the
`tcp.Seq = 1 + (counter & 0x7)` collision above: KCP's reliability depends on
the *carrier* delivering datagrams that are not dedup'd by intermediate
stacks, and the 8-value seq space breaks that assumption.

### Kernel RST window when firewall rules are not applied

A separate but related concern: paqet documents that the host firewall must
drop inbound traffic to the tunnel port so the kernel's own TCP stack does
not RST the synthetic packets ctun is injecting. The integration tests
(T0.2 baseline + this one) do not install firewall rules — that is T4.1's
job. On Linux loopback the kernel may RST our SYN-only packets faster than
the userland recv loop can consume them via pcap, producing intermittent
failures even with the framing issue fixed. The PA baseline test inherits
the same risk; T0.2 did not surface it because the baseline also was not run.

## Suspected obstacles

Each item: `file:lines` — one-line consequence — **owner**.

- `internal/socket/send_handle.go:147` — SYN-only mode reuses one of only 8
  sequence numbers; mid-flow segments will be misclassified as TCP
  retransmissions and silently dropped. **Owner: T1.2 (TFO send path
  rewrite).** Fix: derive Seq from a per-flow counter with full 32-bit
  entropy (the non-SYN branch is a fine template).
- `internal/socket/recv_handle.go:44` — link-layer is hard-coded to Ethernet;
  macOS `lo0` is DLT_NULL and the parser cannot read its own send. **Owner:
  T1.1 (Transport interface) or T1.3 (recv path rewrite).** Same item is in
  T0.2 Appendix C — listing it here for cross-reference, not as new news.
- `internal/socket/recv_handle.go:71-73` — empty-payload packets are dropped
  before reaching upper layers; harmless for current paqet but Phase 1 should
  decide whether SYN-without-payload (e.g. a keepalive) is a thing ctun ever
  emits and, if so, plumb it through. **Owner: T1.3.**
- `internal/socket/send_handle.go:209-216` — `getClientTCPF` reads per-flow
  flags under an RLock on every send; on a SYN-only deployment where the
  iterator is a constant, this is pure overhead. **Owner: T1.1 (Transport
  refactor; minor — performance polish, not correctness).**
- Integration harness (both `smoke_paqet_baseline_test.go` and
  `smoke_syn_only_test.go`) — no firewall rules are installed, so the host
  kernel may RST tunnel-port traffic before pcap delivers it. **Owner: T4.1
  (Firewall interface) or T1.5 (when the SYN-TFO smoke test replaces both
  earlier tests).** Note: this is the most likely reason a future runner will
  see `Test_Smoke_SynOnly` fail even after the seq-entropy and link-layer
  fixes land.

## Recommended next steps for Phase 1

1. **T1.1 (Transport interface refactor)** should expose the link-layer type
   as a Transport-implementation detail, so a future macOS DLT_NULL or a
   Linux-namespace variant can decode without touching the abstract type.
2. **T1.2 (TFO send path)** must rewrite Seq derivation for the SYN case;
   take the non-SYN branch's `seq = time + (counter << 7)` as the baseline,
   adapted to be per-flow so multiple concurrent tunnels do not interleave
   their counters.
3. **T1.3 (TFO recv path)** should make payload-extraction tolerant of
   zero-length SYNs and should drop packets that fail the link-layer parse
   *with a metric*, not silently.
4. **T1.5 (SYN-TFO smoke test)** is the natural moment to add a firewall
   prelude to the integration harness so the kernel-RST window closes.
   Either install minimal `iptables`/`pfctl` rules during the test's setup
   or wire T4.1's `Firewall` interface earlier than the doc currently
   schedules.

## What would be needed to convert this from prediction into measurement

A Linux host (CI runner or a developer VM) with root and `libpcap-dev`,
plus a `tcpdump` capture to confirm what's actually on the wire. The
exact recipe, runnable in a single shell once root is held:

```bash
# Tab 1 — capture loopback traffic for the SYN-only run.
sudo tcpdump -i lo -X -nn -w /tmp/ctun-t0.3.pcap 'tcp and (port 32768 and 65535)' &
TCPDUMP_PID=$!

# Tab 2 — run the test under sudo.
cd /path/to/ctun
sudo go test ./test/integration/ -run 'Smoke_SynOnly' -v -count=1

# Stop the capture, inspect.
sudo kill -INT $TCPDUMP_PID
tshark -r /tmp/ctun-t0.3.pcap -V | less
```

What to look for in the capture:

- Every outgoing tunnel packet has `flags = [S]` only (no ACK, no PSH).
- TCP sequence numbers are *not* all in `{1, 2, 3, 4, 5, 6, 7, 8}` — if they
  are, the seq-entropy concern above is real and Phase 1 must fix it before
  any further data-plane work.
- Inbound packets to the tunnel port are not followed by a kernel-emitted
  RST — if they are, the firewall-rule gap is real and Phase 1 / Phase 4
  scheduling needs to bring T4.1 forward.

If the test passes the round-trip assertion in the harness, **and** the
capture confirms no kernel RSTs and adequate seq entropy, this finding is
empirically refuted and Phase 1's send-path rewrite is a clean rewrite
rather than a bugfix. If it fails, the capture pins down which of the four
suspected obstacles above is the actual blocker.
